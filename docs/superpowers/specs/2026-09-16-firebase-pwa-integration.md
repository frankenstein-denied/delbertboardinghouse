# Firebase + PWA Integration — Spec

## Source

User request (verbatim intent, lightly organized):

1. Create Firebase config; user will input real credentials into env vars later.
2. Import Firebase Auth and Firestore into all respective pages/modules: accounts, dashboard, chats, login.
3. It's a PWA — make the UI mobile responsive.
4. Create an "install app" shortcut in the dashboard.
5. Make logins "remember" (persist across sessions).
6. Business logic: delete posts and reports after 24 hours; expire every chat message after 4 hours.
7. Provide the Firestore security rules.

## Current State (as of this spec)

`delbert-boarding-house-app` is a single-page Next.js 16 (App Router, Turbopack, React 19) mock/prototype generated by v0. All data (`residents`, `posts`, `conversations`) is hardcoded in `app/page.tsx`. There is no backend, no auth, no persistence, no test runner, and (until this plan's setup) no git repository. The "login" experience is a fake local-only `Onboarding` form that never leaves the browser tab.

View → feature mapping (resolves the user's page names to actual code):
- **dashboard** = `HomeView` (the social feed / freedom wall)
- **accounts** = `ProfileView` (resident's own profile)
- **chats** = `ChatsView` (1:1 messaging)
- **login** = currently `Onboarding`; becomes a real Login/Signup screen

Two more existing views (`FriendsView`, `RequestsView`, `ReportsView`) are not named explicitly by the user but sit on the same data model (users, friend requests, reports) and are covered so the app remains internally consistent — wiring only `HomeView`/`ChatsView`/`ProfileView` to live data while leaving `FriendsView` on `residents` mock data would leave the feed populated by real users nobody can actually discover.

## Requirements

### R1 — Firebase config
A single client-side Firebase init module, reading all project config from `NEXT_PUBLIC_FIREBASE_*` environment variables. No real credentials committed. An `.env.local.example` documents every required var with placeholder values.

### R2 — Auth + Firestore wired into every page
- Login/Signup screen backed by Firebase Auth (email + password).
- Dashboard (`HomeView`): posts feed and composer backed by Firestore.
- Chats (`ChatsView`): conversations + messages backed by Firestore, realtime.
- Accounts (`ProfileView`): resident profile read/edit backed by Firestore, sign-out.
- Friends/Requests: backed by Firestore so the feed/chat's authors are real, discoverable users.
- Reports: submission backed by Firestore.

### R3 — PWA, mobile responsive
- Web app manifest + minimal service worker (app-shell caching only — no push notifications, no background sync: not requested).
- Existing UI is already responsive-leaning (mobile nav/menu exist); the new Login/Signup screen and the install button must match that standard down to a 360px viewport.

### R4 — Install shortcut in dashboard
Capture the `beforeinstallprompt` event and surface a visible "Install App" action inside the dashboard shell (sidebar), calling `prompt()` on click. Browsers that never fire the event (iOS Safari, already-installed) must not show a broken/dead button.

### R5 — Remember-me login
Firebase Auth persistence toggle: checked ("Remember me") → `browserLocalPersistence` (default, survives browser restart); unchecked → `browserSessionPersistence` (cleared when the tab closes). Default to checked, matching "make logins remember."

### R6 — Expiry business logic
- Posts and Reports: deleted 24 hours after creation.
- Messages: deleted 4 hours after creation.
- **Ruling:** implemented as Firestore native TTL (a free, built-in Firestore feature — no Cloud Functions, no Blaze billing plan required) on an `expiresAt: Timestamp` field per collection, **plus** a client-side `where('expiresAt', '>', now)` filter on every read. The TTL sweep is why: Firestore's own docs describe TTL deletion as happening "within 24 hours" of the timestamp, not instantly — so relying on TTL alone would let expired posts/messages linger visibly for hours after they were supposed to disappear. The client-side filter makes the *visible* behavior exact regardless of sweep timing; TTL just guarantees the data is *eventually* actually deleted rather than accumulating forever. TTL policies are enabled per collection group from the Firebase Console / `gcloud` **after** the user creates their real project — this plan ships the exact commands in `docs/firebase-setup.md` since it cannot be done against a project that doesn't exist yet.

### R7 — Firestore security rules
A `firestore.rules` file at the repo root covering every collection this plan introduces.

## Data Model

```
users/{uid}
  uid: string
  name: string
  program: string
  room: string
  initials: string
  online: boolean
  createdAt: Timestamp
  // No `friends: string[]` field. Accepting a friend request would need to
  // write the other party's uid into MY array and my uid into THEIRS in one
  // logical operation — a cross-user write that security rules can't grant
  // to a non-owner without either a Cloud Function (reintroduces the Blaze
  // billing requirement R6 explicitly avoids) or a rule so permissive it lets
  // any signed-in user edit any other user's document. Instead, friendship
  // is derived from `friendRequests` docs with status 'accepted' (query both
  // directions and merge client-side) — see below. Single-document writes
  // only, ever.

posts/{postId}
  authorId: string
  authorName, authorProgram, authorRoom, authorInitials: string  // denormalized for feed rendering without N+1 reads
  body: string
  image: string | null
  reactions: { [uid: string]: { label: string; emoji: string } }
  commentsCount: number
  createdAt: Timestamp
  expiresAt: Timestamp        // createdAt + 24h, TTL field

reports/{reportId}          // public (readable by any signed-in resident), rendered anonymously — authorId
  authorId: string           // never displayed, kept only so the create rule can check ownership
  type: string
  reason: string
  description: string
  createdAt: Timestamp
  expiresAt: Timestamp        // createdAt + 24h, TTL field

conversations/{conversationId}      // id = [uidA, uidB].sort().join('_')
  participantIds: string[2]
  participantNames: { [uid: string]: string }
  lastMessage: string
  lastMessageAt: Timestamp

  conversations/{conversationId}/messages/{messageId}
    senderId: string
    text: string
    createdAt: Timestamp
    expiresAt: Timestamp      // createdAt + 4h, TTL field

friendRequests/{requestId}          // id = `${fromUid}_${toUid}`
  fromUid: string
  toUid: string
  status: 'pending' | 'accepted' | 'ignored'
  createdAt: Timestamp
```

## Out of Scope (explicit rulings, not oversights)

- **Comments backend.** The mock UI shows a comment *count* on posts but has no comment thread UI to open one. Building a full comments feature the UI never surfaces would be speculative. `commentsCount` stays a static denormalized field, uninitialized to 0; no comment CRUD.
- **Push notifications / background sync.** Not requested; the service worker caches the app shell only.
- **No role-based accounts, no admin, no hidden dashboards.** Revised after initial build: the user decided against an admin/private-reports model entirely — "easier to maintain, no role based accounts, everyone is a user." `role` was removed from `UserProfile` and from `firestore.rules` (along with the `myRole()`/`isAdmin()` helpers); `reports` are readable by any signed-in resident (`allow read: if isSignedIn();`) and rendered anonymously in the UI — `authorId` stays in the document only to satisfy the create rule's ownership check, never displayed. `ReportsView` shows a live list of all active reports as cards (styled like Freedom Wall posts) below the submission form, not just the submitter's own.
- **New test framework.** The repo has no test runner, no test files, and no CI today (`package.json` has no `test` script; `next.config.mjs` even sets `typescript.ignoreBuildErrors: true`), and this is a rapid-prototype v0-generated codebase. Standing up Jest/Vitest + Firebase Emulator Suite is a substantial, unrequested infrastructure project of its own. **Verification per task in the implementation plan is `npm run build` (Next's own type-check + compile) plus manual code-level review** — not automated tests. This is a deliberate deviation from this org's usual TDD default; task reviewers should not flag "no tests" as a defect for this plan.
- **Live end-to-end testing against real Firebase.** The user has not created a Firebase project yet ("I'll input credentials later"). No task in this plan can be verified against a live Auth/Firestore backend. Code must fail gracefully (clear error, not a white-screen crash) when env vars are placeholder/missing, but functional correctness of the Firebase wiring is a code-review judgment call, not an executed test, until the user supplies real credentials.
- **`NotificationPopover`'s hardcoded content.** Not named in the request; left as decorative mock content to avoid uncontrolled scope growth.
